# BiliTube 架构文档
当前版本：v1.0.0
关联PRD：prd.md

## 1. 架构概述

整体是一条**离线数据流水线 + 纯静态站点**：采集 B 站数据落地的 SQLite 是唯一事实源，归一、过滤、评分、卡片生成都在本地完成，最终导出 JSON 分片，由静态站点消费。

设计原则：

- **单一事实源**：所有中间结果落 SQLite，任何派生产物（JSON 分片、索引、向量）都可从库重建
- **评估可重放**：评分与卡片生成是幂等的纯函数阶段，改了权重或提示词可以只重跑这一段，不重复采集
- **外部依赖可降级**：字幕、评论、弹幕、LLM 任一失败都不阻塞主流程，只在卡片上降低"评估依据"等级
- **无运行时后端**：站点构建后就是一堆静态文件，不部署数据库，不存用户数据

## 2. 模块划分

| 模块 | 职责 | 依赖 |
| ---- | ---- | ---- |
| A 采集 collector | 调 B 站接口，落原始表，限速与断点 | SQLite、代理 |
| B 归一 normalizer | 去重、系列合并、搬运判定、失效过滤 | collector 产物 |
| C 评估 scorer | 硬过滤、分位归一、LLM 分类与打分 | normalizer 产物、LLM |
| D 卡片 cardgen | 生成摘要、适合谁、前置、时效、主题归类 | scorer 产物、LLM |
| E 导出 exporter | 生成站点 JSON 分片、搜索索引、向量文件 | 全库 |
| F 站点 web | 静态页面、筛选、搜索、本地收藏 | exporter 产物 |
| G 运维 ops | 日志、统计报告、失败重试与断点管理 | 全链路 |

模块之间只通过 SQLite 表与导出文件通信，不互相 import 业务逻辑。

## 3. 数据流 / 调用链路

```text
B站公开接口
   │  (限速 1-2 req/s，断点续采)
   ▼
[collector] ──► raw_topics / raw_videos / raw_comments / raw_danmaku / raw_subtitles
   │
   ▼
[normalizer] ──► videos（去重、系列合并、搬运标记、失效剔除）
   │
   ▼
[scorer]
   ├─ 硬过滤（规则 + LLM 分类）
   ├─ 分位归一（分区 × 时长档）
   └─ LLM 内容打分（字幕 / 弹幕 / 评论 / 简介降级）
   ▼
[cardgen] ──► cards（摘要、why、适合谁、前置、难度、时效、主题）
   │
   ▼
[exporter] ──► web/public/data/videos.json、topics.json、meta.json
   │
   ▼
[web] Next.js build ──► 静态站点
```

## 4. 技术选型

| 组件 | 选型 | 理由 |
| ---- | ---- | ---- |
| 运行时 | Python 3.12 | 本机已装；类型提示与 asyncio 成熟 |
| HTTP | httpx（显式代理） | 本机访问 B 站必须走 `127.0.0.1:7890`，httpx 代理支持清晰 |
| 存储 | SQLite（WAL） | 单机、零部署、可断点；数据量在百万行内 |
| 导出 | JSONL + JSON 分片 | 站点直接消费，无需运行时查询 |
| LLM | provider 抽象，默认 DeepSeek | 中文理解好、单价低；可切换 Claude / OpenAI |
| Embedding | bge-small-zh-v1.5（512 维，CPU）——**当前未启用** | 本地推理零调用成本，300–800 条规模毫秒级；1360 条规模下关键词匹配已够用，向量召回留作后续 |
| 站点 | Next.js 15 App Router + 手写 CSS 设计令牌（无 UI 库），`output: export` | 静态导出；视觉需要完全可控，卡片与排版不套现成组件 |
| 搜索 | 浏览器端关键词包含匹配（minisearch / 向量检索未启用） | 1360 条全量过滤实测 < 100ms，不需要额外索引 |
| 测试 | pytest + 快照测试 | 评分与卡片字段结构需回归保护 |
| CI | 现有 markdownlint + shellcheck，后续加 pytest | 沿用模板 |

## 5. 部署结构

- 开发与生产（v1.0）：**单机 Windows**，`python -m bilitube ...` 跑流水线，`npm run build` 出静态站
- 可选发布：静态产物可直接部署到 Vercel / Cloudflare Pages，构建时不依赖数据库
- 环境变量：`.env` 保存 `BILI_SESSDATA`、`LLM_API_KEY` 等，`.gitignore` 已排除
- 数据不在仓库内：`data/` 目录加入 `.gitignore`，发布只带导出的 JSON

## 6. 风险与约束

- **字幕覆盖率未知**：未登录时字幕接口返回空。若登录态下覆盖率仍低，第三层评估退化为"弹幕 + 评论 + 简介"，卡片必须标注评估依据，否则会高估可信度
- **B 站风控**：搜索、详情、评论接口在密集请求下可能返回 `-352`，需要缓存 + 退避 + 请求间隔
- **LLM 误判**：标题党识别与"是否搬运"的判断会有错，用人工抽检校准，不做全自动发布
- **搬运与拼凑**：AI 教程区大量"合集搬运"，仅靠规则识别率低，必须 LLM 参与
- **数据时效**：AI 领域内容半年就可能过时，卡片必须带时间标签
- **无登录态下的评论分页**：深度翻页受限，只取热门评论，不追求全量

## 7. ADR 记录（追加式，不修改历史）

### ADR-001 数据源与字幕策略

- 上下文：需要从 B 站获取视频元数据、评论、弹幕与字幕；未登录时可用的接口有限
- 备选方案：
  1. 纯公开接口，不碰登录态：简单、稳定，但拿不到字幕，第三层评估缺失
  2. 公开接口 + 用户提供的本地 Cookie：可拿到字幕，但引入账号风险
  3. 音频下载 + 本地 ASR：不依赖字幕接口，但成本与工程量高一个量级
- 决策：选定方案 2，Cookie 只存本地 `.env`，只读不写，不进数据库、不进导出包
- 取舍：获得内容级评估能力，代价是用户需要维护一个 Cookie
- 遗留风险：字幕接口的覆盖率与稳定性未知，需要先做 20 条视频的覆盖率测试

### ADR-002 评分体系：分位归一 + 内容分主导

- 上下文：固定阈值（如收藏率 > 2%）在实测中会放过明显的拼凑引流内容——样本视频收藏率 4.45%、点赞率 1.64%，但标题为"全 748 集、最全最细、七天速成"
- 备选方案：
  1. 固定阈值：简单直观，但不同分区、不同时长的基线差异大，易误判
  2. 分区内百分位：同分区同时长档内比较，能消除基线差异
  3. 纯 LLM 打分：能看内容，但成本高、方差大、无法解释
- 决策：选定方案 2 + 方案 3 结合：机器信号取分位，内容分由 LLM 给出，内容分权重 0.40
- 取舍：需要足够大的同分区样本才能算分位；样本不足时退化为绝对阈值并标注
- 遗留风险：分位依赖候选池规模，候选池本身有偏（只来自关键词搜索）

### ADR-003 存储：SQLite 单一事实源

- 上下文：需要断点续采、幂等重跑、可重建导出
- 备选方案：
  1. 直接用 JSONL 文件：简单，但去重与关联查询困难
  2. SQLite：单文件、事务、索引齐全，查询方便
  3. Postgres：功能强，但单机项目引入运维成本
- 决策：选定方案 2
- 取舍：需要写少量 SQL；换来断点、事务与可重建性
- 遗留风险：SQLite 不适合并发写，采集与评估需串行或分库

### ADR-004 站点：静态导出，无后端

- 上下文：单机产品、无账号、数据只读
- 备选方案：
  1. 静态导出（Next.js `output: export`）：零运维、可托管任意静态托管
  2. SSR / 服务端：可做动态推荐，但需要部署与数据库
  3. SPA 直读 JSON：最轻，但首屏与 SEO 差
- 决策：选定方案 1
- 取舍：放弃服务端个性化推荐，个人数据全部存浏览器
- 遗留风险：数据量增长到数万条时，全量 JSON 会变大，需要按主题分片

### ADR-005 半自动策展与人工抽检

- 上下文：LLM 判定有误判，全自动发布风险高
- 备选方案：
  1. 全自动：快，但榜单会被噪音污染
  2. 全人工：质量最高，不可持续
  3. 半自动：LLM 初筛 + 人工抽检 + 定期复核
- 决策：选定方案 3，抽检比例与一致率写入统计报告
- 取舍：每条入库都需要人工确认一次，换来可控的质量
- 遗留风险：人工环节会成为更新频率的瓶颈

### ADR-006 时间窗口与"经典位"

- 上下文：AI 领域内容时效性强，但基础内容（Transformer 原理、深度学习入门）长期有效
- 备选方案：
  1. 只做近 24 个月：时效性好，会丢掉基础经典
  2. 全历史：会混入大量过时内容
  3. 24 个月为主 + 历史经典少量保留
- 决策：选定方案 3，经典位需同时满足"高收藏率分位"与"内容分达标"，且人工确认
- 取舍：增加一条人工判断路径，换来基础内容的连续性
- 遗留风险：“经典”的判定标准会随领域变化，需要定期复核

### ADR-007 采集安全与账号隔离

- 上下文：用户担心采集会影响自己的 B 站账号。B 站对未登录请求只做 IP 级风控，对携带 Cookie 的异常流量才会关联账号
- 备选方案：
  1. 全程登录态采集：数据最全，但全部请求与账号绑定，风险最高
  2. 全程匿名：最安全，但拿不到字幕
  3. 匿名为主 + 字幕单独登录通道：风险与收益折中
- 决策：选定方案 3。除字幕外全部匿名；请求走**直连**（家庭宽带 IP），不走代理，避免"异地登录"触发账号风控；字幕请求串行、限速 1 req/s、只对最终入选的数百条视频执行，随时可停
- 取舍：字幕覆盖率可能不足，第三层评估需要降级
- 遗留风险：B 站用户协议对抓取有限制，个人非商业低频使用实践中风险低，但无法给出 100% 保证；一旦 `-352` 比例超过 5% 即自动暂停采集

### ADR-008 采集预算与节奏

- 上下文：需要估算请求总量与对 B 站的压力
- 备选方案：
  1. 一次性全量：快，但瞬时请求密集，易触发风控
  2. 分阶段、分多天：慢一点，但把风险摊平
- 决策：选定方案 2。预估总请求约 1.2 万次（搜索 2000 + 详情 3000 + 评论 3000 + 弹幕 3000 + 字幕 800），按 1.5 req/s 分 2–3 天完成
- 取舍：首版出数慢半天到一天
- 遗留风险：候选池扩大后请求量线性增长，需要按比例延长节奏

### ADR-009 收藏率口径失效与分位方案的必要补充

- 上下文：TASK-004 实采数据发现 B 站"收藏数"与"播放数"口径不一致，收藏率可以超过 100%。样例：`BV1ug3qzhEp9` 播放 1,141,309、收藏 1,286,533，收藏率 112.7%；`BV1boqBBEENs` 收藏率 49.9%
- 备选方案：
  1. 直接用收藏率做绝对阈值：口径不统一，会产生荒谬值
  2. 先做截断再算：治标不治本，仍是绝对值逻辑
  3. 分位归一（ADR-002 已有）+ 明确记录口径缺陷：分位只依赖排序，对量纲不敏感
- 决策：维持分位归一，同时在数据层保留原始计数与"收藏/点赞比"作为辅助特征；卡片文案不展示"收藏率"，只展示综合评分与推荐理由
- 取舍：用户看不到可解释的单一数字，需要用"为什么值得看"的文字弥补
- 遗留风险：若 B 站后续调整口径，分位仍然可用，但历史数据的可比性会下降，需要在采集时间戳上做标记

### ADR-010 未登录评论接口受限，弹幕升级为第二层主力

- 上下文：实测未登录调用 `/x/v2/reply`，尽管视频有 622 条评论，接口只返回 3 条（`page.count=622`，但 `replies` 长度 3），翻页返回 0 条
- 备选方案：
  1. 为评论单独引入登录态：数据最全，但与"账号零接触"的目标冲突
  2. 接受 3 条热评：信号极弱，无法判断口碑
  3. 弹幕替代：未登录可拿约 1200 条，反映真实观看体验与槽点
- 决策：选定方案 3。第二层文本理解以"标题 + 简介 + 弹幕 + 少量热评"为输入，卡片 `evidence` 字段标注 `danmaku`
- 取舍：失去长评论里的深度观点，换来零账号风险
- 遗留风险：弹幕短、噪音大、易被梗覆盖，需要 LLM 做清洗与归纳

### ADR-011 搜索接口选型：弃用 wbi 版，改用旧版接口

- 上下文：首次全量采集用 wbi 版搜索，前 39 页正常，之后接口持续返回 `code=0` 但 `data` 只有 `v_voucher`——这不是空结果，是风控挑战。旧版 `/x/web-interface/search/type` 在同等频率下仍可返回数据
- 备选方案：
  1. 继续用 wbi 版并实现 wbi 签名：可行，但签名逻辑复杂且仍可能被挑战
  2. 改用旧版接口：实测字段一致、可用
  3. 两版轮流：增加复杂度，收益不明
- 决策：选定方案 2。旧版为主，并显式识别 `v_voucher`（当 `data` 中无 `result` 字段时判定为挑战，计入风控统计并重试）
- 取舍：旧版接口没有文档保证，存在被下线风险，需要在客户端保留切换点
- 遗留风险：即使降到 0.4 req/s，249 页里仍有 27 页返回 HTTP 412（IP 级限流），说明限速不是唯一变量，需要"失败页单独重试"机制

### ADR-012 采集产物的两个已知缺陷

- 上下文：首轮 250 页采集得到 3652 个候选视频，检查后发现两个数据质量问题
- 发现：
  1. 搜索接口不返回 `coin`（投币）字段，3652 条全是空值，投币率必须靠详情接口补齐
  2. 关键词搜索噪音大：只有 57.6% 的标题命中 AI 相关词，播放量前 5 的视频全是娱乐内容（死侍、老番茄、滑板），说明搜索排序会混入热门但与主题无关的内容
- 决策：候选池不直接作为成品，必须经过"标题相关性过滤 + 详情补齐 + 评分"三步；投币率在补齐前不参与任何打分
- 取舍：详情补齐会让请求量从 250 页扩到约 3000 次单视频请求，需要分批
- 遗留风险：标题相关性过滤会误杀"标题朴素但内容优质"的视频，需要 LLM 结合简介二次判断

### ADR-013 机器分先行：内容分接入前的权重方案

- 上下文：完整评分公式里内容分占 0.40，但那一步需要 LLM 与 (可能的) 字幕，晚于筛选阶段。若等全部就绪再出分，前面所有环节都无法验证
- 备选方案：
  1. 等内容分就绪再统一打分：链路长，问题发现得晚
  2. 先用机器分单独归一（收藏 0.30 / 投币 0.25 / 点赞 0.15 / 讨论 0.15 / 播放 0.15），内容分接入后再重算 total
  3. 用播放量临时排序：与"反算法"目标冲突
- 决策：选定方案 2。`scores.machine` 与 `scores.total` 分开存，内容分接入时只重写 `content` 与 `total`，不动 `machine`
- 取舍：当前榜单只看互动质量，无法区分"包装精美的水教程"
- 遗留风险：机器分高但内容空洞的视频会暂时排在前面，需要内容分层落地后复核

### ADR-014 分位分组与低样本退化

- 上下文：实采 1360 条通过视频，按"分区 × 时长档"分组后，有 254 条（19%）落在样本不足 30 的组里（如"财经商业 × >90min"）
- 备选方案：
  1. 小样本组照常算分位：十几个样本排出的分位没有统计意义
  2. 小样本直接剔除：会误删小众赛道的优质内容
  3. 退化为全站分位并标注：保留内容，暴露不确定性
- 决策：选定方案 3，`scores.flags` 打 `low_sample` 标记，前端可据此提示
- 取舍：小众分区与全站基线比较，可能被高估或低估
- 遗留风险：低样本组会随候选池扩大而变化，分数需要定期重算

### ADR-015 封面图直连 B 站 CDN，不落本地

- 上下文：卡片需要视频截图，否则用户第一眼认不出这是视频。B 站封面在 `i0-i2.hdslb.com`，实测带非 B 站 Referer 返回 403，无 Referer 返回 200；同一 URL 加 `@672w_378h_1c.webp` 后缀可拿到 672×378 的 webp 缩略图
- 备选方案：
  1. 把 1360 张封面下载进 `web/public/covers/`：可控但仓库体积从 1.3MB 涨到约 300MB，且失去静态托管的轻量优势
  2. 直连 CDN + `referrerPolicy="no-referrer"`：零存储，图片随 B 站源更新
  3. 自建图片代理：需要运行时，与纯静态部署冲突
- 决策：选定方案 2。`raw_videos.cover` 存归一化后的 https 绝对地址（`normalize_cover`），前端 `coverUrl()` 追加尺寸后缀，`<img>` 显式设置 `referrerPolicy="no-referrer"` 与 `loading="lazy"`
- 取舍：依赖 B 站 CDN 可用性与防盗链策略；若策略变化，卡片会集体变成占位底色（有降级样式，不会破版）
- 遗留风险：封面版权属于 UP 主，本站只做引用，不转存、不二次分发

### ADR-016 站点视觉从「暗色卡片流」改为「编辑型策展版面」

- 上下文：首版站点是深色面板 + 圆角卡片 + 蓝色强调色，信息正确但观感像内部工具：缺少层级，卡片不像视频，页面没有回答「这是什么、凭什么信」两个问题
- 备选方案：
  1. 在暗色卡片流上做微调：成本低，但气质问题解决不了
  2. 视频站常规形态（B 站/YouTube 风格）：与源站同质，丢失「精选」的差异
  3. 编辑型策展版面：纸张底色 + 墨色正文 + 单一朱红重点色，衬线标题、发丝线分隔、无阴影堆叠，封面成为视觉主角
- 决策：选定方案 3。设计令牌集中在 `web/app/globals.css` 的 `:root`；标题用衬线栈（Noto Serif SC → Songti SC → SimSun），正文与控件用系统无衬线；页面上出现三处强层级：编辑首选头条、卡片封面、详情页「编辑手记」引文块
- 取舍：纸色 + 衬线的方案依赖本机中文字体，缺少 Noto Serif SC 的机器上会退到 SimSun，观感有差异但不破版；放弃暗色模式以换取一致的光感
- 遗留风险：强调色只有朱红一种，后续若要新增状态色（如评分区间）需要扩充令牌，不能就地写死色值

### ADR-017 站点主色改为「翠绿」，配色收敛成单一令牌入口

- 上下文：ADR-016 的视觉重做用朱红 `#b23a2b` 作唯一强调色，但配色本身没做过并列比较。随后在 `previews-colorways/` 里做了 15 套同版式配色，用户选定第 15 号「翠绿」方案
- 备选方案：
  1. 保留朱红 + 暖纸底：用户反馈暖色系浅底"看不清"，辨识度不足
  2. 中性色对照（暖纸 / 米白 / 冷灰，共用主色只换底子）：实测偏闷，已移除
  3. 提高主色饱和与明度、把底色从暖纸转浅青白：`#2f7a55` + `#f2f7f4`
- 决策：选定方案 3。同时把 `globals.css` 里剩余的硬编码色（封面占位、骨架屏、时长角标、播放器底色、播放键底）全部提成变量：`--placeholder` / `--skeleton` / `--overlay` / `--on-overlay` / `--player`，换肤从此只需改 `:root` 一处
- 取舍：冷底 + 绿主色比纸色少一点暖意，但对比度整体更高（正文 13.1:1、次要文字 5.1:1、辅助 4.5:1、主色上的白字 5.2:1），小字号信息更清楚
- 遗留风险：强调色只有一档深浅，后续若要区分「教程 / 实战 / 测评」等状态，需要再补语义色令牌（如 `--ok` / `--warn`），不要就地写十六进制

### ADR-018 配方（preset）与引擎解耦

- 上下文：v0.1.0 里「按什么标准跑」散在两处——`config/` 是外置的，但打分权重、时长分桶、小样本阈值和生成卡片的 prompt 都焊在 `scoring.py` / `llm.py` 里。结果：改权重必须改代码、跑测试，也无法只公开引擎而保留配方
- 备选方案：
  1. 配方留在代码里，另开分支手工做「公开版」：两份代码必然漂移
  2. 全部外置成环境变量：参数十来个，不可读也不可版本化
  3. 一个目录装一份完整配方（preset），代码只认目录结构
- 决策：选定方案 3。`presets/<name>/` 固定五个文件（preset.json / keywords.txt / rules.json / scoring.json / prompt.md），`bilitube/preset.py` 负责加载与校验（权重和必须为 1.0）。引擎保留同名默认值（`scoring.WEIGHTS/BUCKETS/MIN_GROUP_SIZE`、`llm.SYSTEM_PROMPT`），仅在未传 preset 时生效，保证既有脚本与测试不破坏
- 配套修复：`score_all` 的 upsert 原本把 `content` 写成 NULL，重跑 `score` 会抹掉 card 阶段算出的 1360 个内容分；改为 `COALESCE` 保留，并在有内容分时按 0.6/0.4 重算 total
- 取舍：配置从两处收敛到一处，代价是多一层间接；prompt 变成 md 后改它不再触发类型检查
- 遗留风险：喂给模型的证据（标题/简介/弹幕采样）仍由 `build_prompt` 拼装，若将来要让配方控制「看什么证据」，需要再抽一层

### ADR-019 暗色模式：跟随系统 + 手动覆盖

- 上下文：ADR-016 曾以「纸色方案在暗色下会垮」为由暂缓暗色。后来在 `previews-colorways/` 里做出「夜航」配色，证明同一套结构在深底上可以成立
- 备选方案：
  1. 只跟随 `prefers-color-scheme`：零 JS，但用户无法手动切回浅色
  2. 只做手动切换：首屏依赖 JS，未开 JS 时永远是浅色
  3. 两者并存：媒体查询兜底，`data-theme` 覆盖
- 决策：选定方案 3。`@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) {…} }` 跟随系统；切换按钮往 `:root[data-theme]` 写 `dark` / `light` 并存进 localStorage。首帧前用 body 顶部的一段同步脚本套用，避免刷新时闪白
- 取舍：暗色是同一组变量的第二份取值，新增令牌时两处都要补（文件里已注明）。logo 是「镂空 + 透出页面底色」，因此在深底上电视轮廓自动变暗，不需要第二套图标
- 遗留风险：封面缩略图来自 B 站，亮底图片在暗色下偏晃眼，目前只压了 `brightness(.94)`；若将来做多主题换肤，需要重新评估图片处理策略

### ADR-020 托管选型：Cloudflare Pages + 自有域名

- 上下文：站点是 `output: "export"` 的纯静态产物（1364 页 + 1.37MB 数据 JSON）。境内服务器需要 ICP 备案，本项目不具备条件，因此只能选境外托管。候选：Vercel Hobby、Cloudflare Pages Free、自建 VPS
- 备选方案：
  1. Vercel Hobby：Next.js 体验最好，但月带宽 100GB、明确禁止商业用途，且 `*.vercel.app` 在国内被污染
  2. Cloudflare Pages Free：带宽不限、构建 500 次/月、无商用限制、自带无 cookie 统计；`*.pages.dev` 同样被污染
  3. 自建 VPS：可控但需长期维护，成本高，单个 IP 被墙后无退路
- 决策：选方案 2，配自有域名。构建配置 Root=`web`、Build=`npm ci && npm run build`、Output=`out`、`NODE_VERSION=20`。缓存与安全头写在 `web/public/_headers`，随构建产物一起发布
- 取舍：放弃 Vercel 的 Next.js 原生能力（ISR、图片优化），但项目已锁定静态导出，这些能力本来也用不上；域名是唯一固定成本
- 风险：两家都需要自定义域名才能在国内稳定访问，延迟约 200–400ms；静态产物可平滑迁移，迁移成本仅限平台配置，因此选错的代价很低

### ADR-021 采集默认限速从 1.5 降到 0.8 req/s

- 上下文：ADR-008 定的默认限速是 1.5 req/s，与 `NOTICE.md` 写的「默认 0.8、请勿调高」不一致。2026-11-10 一次周更实测：同一关键词第 1、2 页成功，第 3 页返回 `HTTP 412`（风控），整轮采集立即中止——3 个请求就被拦，说明 1.5 对当前 IP 状态偏高
- 备选方案：
  1. 保持 1.5，靠 `.env` 覆盖：文档与代码继续漂移，新克隆者默认高风控风险
  2. 降到 0.8，与文档和 NOTICE 对齐：牺牲约一倍的采集速度（60 页从 40 秒变 75 秒），换更低的 412 概率
  3. 降到 0.3–0.5：更稳，但一轮全量采集要更久
- 决策：选方案 2，默认 0.8；需要更慢时用 `RATE_LIMIT_RPS` 环境变量覆盖（建议 0.5），不改代码
- 取舍：周更 3 页 × 20 关键词的增量采集，总耗时从约 40 秒增加到约 75 秒，可接受
- 遗留风险：412 是 IP 级限流，限速不是唯一变量（ADR-008 已记录过 0.4 req/s 仍有 27 页失败）；真正的解法是配 `BILI_SESSDATA` 带登录态，以及失败页单独重试

### ADR-022 采集必须携带匿名设备指纹（buvid3/buvid4）

- 上下文：2026-11-10 周更时，即使把限速降到 0.8 req/s、等待 1.5 小时冷却，搜索接口仍在第一个请求就返回 `HTTP 412`。逐项实测：主站首页 200、`nav` 200、搜索页 HTML 200，**只有搜索 API 稳定 412**；补上 `buvid3`/`buvid4` 两个设备 cookie 后立刻恢复 `code=0` 并返回 20 条结果
- 备选方案：
  1. 要求配置 `SESSDATA` 账号 cookie：效果最好，但需要用户登录、有账号风控与隐私成本
  2. 取匿名设备指纹：无需登录，`GET /x/frontend/finger/spi` 返回 `b_3`/`b_4`
  3. 改抓搜索页 HTML 再解析：慢且随页面改版失效
- 决策：选方案 2。`BiliClient.warmup()` 在采集前取一次指纹，之后所有请求带 `buvid3`/`buvid4`；配置了 `SESSDATA` 时一并携带。warmup 失败不致命，只是风控概率更高
- 取舍：每个进程多一次请求；设备指纹每次运行会变（属正常），不影响统计数据
- 遗留风险：412 仍可能是 IP 级封禁，指纹不是万能解；长期稳定仍建议配 `SESSDATA`
